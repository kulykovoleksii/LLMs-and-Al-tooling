# Операційна система навчання

## Ціль і межі

Ціль — підійти до перенесеного курсу з готовими базовими навичками та власним
інженерним проєктом. Маршрут спирається на теми брошури: надійні LLM-виклики,
агенти й інструменти, retrieval/context, оцінювання та governance.

За замовчуванням маршрут інтенсивний: 4 тижні по 30 годин зосередженої роботи
(6 продуктивних годин на день, 5 днів на тиждень). З перервами це приблизно
повний робочий день. Це навчальний спринт, а не вимога постійно працювати в
такому темпі. Якщо фактичний день коротший, збережи порядок тем і критерії
приймання, а не намагайся компенсувати недосипом. Не потрібно вчити кожен
фреймворк або провайдера: спершу опануй принципи й один стек.

## Налаштування системи

Потрібні:

- Git і репозиторій для навчального capstone (окремий або папка в репозиторії
  цього навчального маршруту).
- Python 3, редактор із AI-помічником, середовище віртуальних залежностей.
- Тести й форматування, автоматичний запуск тестів при кожній значущій зміні.
- Один LLM API або локальна модель. Не підключай кілька провайдерів, поки
  не з'явиться задача для порівняння.
- Трекер — Markdown-файли в репозиторії достатні; не починай з побудови
  окремої системи продуктивності.

Фіксуй версії залежностей і модель/параметри в конфігурації. API-ключі зберігай
тільки в локальному environment/secret store, не в коді, промптах, логах чи Git.
Перші retrieval-експерименти проводь на публічних або синтетичних документах.

## Щоденний і тижневий ритм

Орієнтир на продуктивний день (6 годин, перерви окремо):

- **Навчання — 1 год.** Одна тема з офіційної документації або першоджерела;
  запиши 3 твердження та посилання.
- **Практика — 2 год.** Реалізуй маленький приклад самостійно.
- **Інтеграція — 2 год.** Додай перевірений результат до capstone.
- **Перевірка й нотатки — 1 год.** Запусти тести, зроби AI review, перевір
  зауваження самостійно й занотуй рішення.

П'ятницю кожного тижня використовуй для інтеграції, повного запуску перевірок,
демо та підсумку. Не переходь далі, якщо ключовий deliverable не працює.
Якщо відстав, скороти необов'язкове поглиблення, але не тести, gate чи сон.

## Роль AI

Використовуй AI в чотирьох режимах:

- **Наставник:** пояснює концепцію, ставить запитання, не видає відповідь
  одразу.
- **Планувальник:** ділить зафіксований результат на маленькі задачі.
- **Рев'юер:** шукає граничні випадки, відмови, ризики та пропущені тести.
- **Екзаменатор:** перевіряє, чи можеш пояснити рішення без підказок.

Не проси AI просто «побудувати всю систему». Попроси невелику зміну, вимоги,
тести й пояснення. Переглядай кожен diff; не приймай код, який не можеш
пояснити. Текст із web-сторінок, PDF, email чи retrieval вважай недовіреним
вводом, а не інструкціями для AI.

### Базовий промпт наставника

```text
Ти — мій вимогливий наставник з LLM systems engineering.
Моя ціль цього тижня: [результат].
Мій поточний рівень/код: [контекст].
Спочатку постав максимум 3 уточнювальні запитання, якщо бракує даних.
Пояснюй малими кроками й спершу запитуй, що я вже розумію.
Не вигадуй API, джерела чи результати тестів. Якщо не впевнений —
познач невизначеність і запропонуй перевірку в офіційній документації.
Не пиши весь проєкт за мене. Для коду дай мінімальний крок,
критерій приймання та конкретні тести.
```

### Промпт для декомпозиції

```text
Перетвори цей результат на план максимум із 5 малих задач:
[результат і обмеження].
Для кожної задачі вкажи: передумову, очікуваний diff, тест/перевірку,
ризик і ознаку завершення. Не додавай задач поза результатом.
```

### Промпт для code review

```text
Зроби adversarial review цього diff відносно вимог нижче.
Шукай помилки логіки, валідації, таймаути/повтори, витік даних,
небезпечне виконання інструментів, недетерміновані тести та прогалини
в спостережуваності. Не переписуй код. Для кожного зауваження наведи
файл/рядок, сценарій відтворення, вплив і тест, який підтвердить проблему.
Якщо підтверджених проблем немає, скажи це прямо.
Вимоги: [вимоги]
Diff: [вставити diff без секретів]
```

### Промпт для усного заліку

```text
Перевір мене по темі [тема] як на code/design review.
Став по одному запитанню, чекай моєї відповіді, потім вкажи прогалини
й попроси пояснити trade-off. Не підказуй відповідь до моєї спроби.
Наприкінці дай оцінку 0–2 за точність, обґрунтування та межі застосування.
```

## Контроль якості та метрики

На кожну зміну зберігай відтворюваний приклад або тест. Для LLM-функцій:

- валідуй форму виходу кодом, не лише промптом;
- веди golden set із прикладами й очікуваними властивостями;
- зберігай версію промпту, назву/версію моделі та параметри;
- вимірюй якість, помилки, latency і приблизну вартість;
- порівнюй із простим baseline, включно з варіантом без LLM;
- фіксуй обмеження вибірки та не трактуй малий тест як доказ загальної якості.

Персональний gate для просування далі:

1. Можеш пояснити архітектуру і один відхилений альтернативний варіант.
2. Тести проходять; немає секретів або незрозумілих змін у diff.
3. Є щонайменше один edge/failure test для нової поведінки.
4. Для AI-функції є вимірювана якість на зафіксованих прикладах.
5. Заповнений тижневий підсумок і визначений наступний крок.

Це навчальні критерії, а не гарантія production-readiness.

## Режим очікування дати

Після місячного маршруту не потрібно нескінченно додавати нові технології.
Підтримуй темп 2–3 години на тиждень:

- один короткий цикл: змінити одну річ, прогнати regression suite, переглянути
  витрати/latency;
- один цикл пояснення: 10 хвилин усно пройти архітектуру або розібрати
  неочікуваний результат;
- раз на місяць перевірити офіційні release notes провайдера й оновити
  залежність лише за конкретної потреби.

Коли з'явиться дата курсу, використай останні 2–4 тижні для повторення слабких
місць і перетвори capstone на навчальний companion. Під час курсу пріоритет —
його завдання та зворотний зв'язок викладачів; не намагайся паралельно
перебудувати стек.
