# Capstone: персональний knowledge assistant із контрольованими діями

## Навчальна задача

Побудувати невеликий асистент, який класифікує запит, за потреби шукає доказ
у контрольованій колекції документів, формує відповідь із посиланнями та
пропонує обмежену дію на кшталт створення чернетки. Побічна дія виконується
лише після підтвердження людиною.

Це безпечна навчальна задача, а не припущення про твою робочу потребу. Почни
з синтетичних чи публічних документів. Якщо маєш реальний use case, підміняй
сценарій лише після того, як сформулюєш дозволені дані, користувачів,
наслідки помилки та критерій успіху.

## Межі MVP

**Включити:**

- вхідний запит → структурована категорія/намір із валідованою схемою;
- відмова або уточнення, якщо запит невизначений;
- retrieval із allowlisted колекції та посилання на використані фрагменти;
- обмежені типізовані tool calls із перевіркою аргументів;
- людське підтвердження до будь-якого запису;
- golden set, regression run, latency/вартість та журнал без секретів.

**Не включати в MVP:**

- autonomous actions, довільне виконання коду чи довільний доступ до файлів;
- production користувачів, особисті/робочі документи чи фінансові дані;
- fine-tuning без аргументованої потреби й погодженого набору даних;
- multi-agent архітектуру або кілька провайдерів без виміряної причини.

## Архітектурний ескіз

```text
request
  -> input validation
  -> deterministic routing / structured LLM classification
  -> retrieval over allowlisted documents (when needed)
  -> answer with evidence OR explicit abstention
  -> proposed tool action
  -> checker + authorization + human approval
  -> tool execution with timeout/idempotency
  -> safe trace + evaluation
```

Модель не є межею безпеки. Перевірки доступу, схеми, ліміти, підтвердження,
timeouts та обробка помилок мають виконуватись звичайним кодом.

## Послідовність інкрементів

1. **Classifier:** схема, валідатор, baseline rules, тестовий набір.
2. **Tool proposal:** агент лише пропонує дію; нічого не змінює.
3. **Approval gate:** дія потребує явного підтвердження; повторний запит
   не створює дубль.
4. **Knowledge retrieval:** пошук повертає фрагменти з джерелом; відповідь
   може abstain.
5. **Evaluation:** golden set ловить зміну якості при зміні prompt/model.
6. **Hardening:** межі бюджету, помилки провайдера, timeout, логи й README.

## Перевірки приймання

- Невалідний LLM-вихід не доходить до інструмента.
- Незнайомий тип інструмента й аргумент поза allowlist відхиляються.
- Текст у знайденому документі, який просить ігнорувати правила або розкрити
  секрет, не змінює політики чи прав асистента.
- Без релевантного джерела асистент чітко повідомляє про невизначеність.
- Retry не виконує запис вдруге.
- До/після зміни можна порівняти на однаковому наборі прикладів.
- Перевищення бюджету або недоступність моделі спричиняє контрольовану
  помилку/ескалацію, не успішний вигаданий результат.

Метрики та пороги обери на початку етапу оцінювання відповідно до наслідків
помилки. Не оголошуй навчальну вибірку доказом production якості.
